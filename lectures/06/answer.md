## 宿題

<!-- 基礎・実装・発展のどれか1つに取り組めば完了です。 -->

- 取り組んだレベル：実装
- やったこと：  
引数に範囲外の回を指定した場合、make_quiz で return により文字列を返すパターンと、raise により例外を発生させるパターンの2パターンで挙動を確認した。  
return の場合は「第〇回の用語が見つかりませんでした。」という文字列を返すように実装し、raise の場合は例外を発生させるように実装した。  
それぞれの実装パターンで app/mcp_server.py に make_quiz を公開し、以下のコマンドを実行して trace の内容を確認した。  
「uv run python -m app.mcp_agent --trace "第99回のクイズを作って"」
- 結果：  
■return  
モデルの回答：  
「指定された第99回の用語および確認問題は、講座の用語集に見つかりませんでした。  
AIE2026の講座で対象となっている回（例えば第1回〜など）の確認問題であれば作成できますので、ご希望の回を指定してください。」  
trace：  
[tool call]   glossary_make_quiz({'lecture': 99})  
[tool return] glossary_make_quiz -> 第99回の用語が見つかりませんでした。  
■raise  
モデルの回答：  
「第99回という回は講座のカリキュラムや用語集に存在しないため、確認問題を作成することができません。現在ご用意している回や、学習したい具体的な用語（例：LoRA、RAGなど）を教えていただければ、対応する用語の解説やクイズの作成を行うことができますので、ぜひお知らせください。」  
trace：  
[tool call]   glossary_make_quiz({'lecture': 99})  
[tool error]  glossary_make_quiz -> Error executing tool make_quiz
- 気づき・疑問：  
return と raise で trace に出力されたツールの実行結果は異なっていたが、モデルの最終的な回答に大きな差は見られなかった。  
raise の場合は具体的な用語を指定することも提案していたが、複数回実行した場合は return でも同様の回答を得られる可能性もあると考えた。  
今回の実行結果では大きな違いは発生しなかったが、より複雑な質問や複数のツールを使用する場合にも同じ挙動になるのか疑問に思った。  
また自分の視点では、 raise より return の出力の方が何が発生したのか理解しやすいと感じた。  
エラー の内容を確認しても失敗した原因の理解に時間が掛かったため、モデルにとっても明確なメッセージの方が情報を整理しやすいのではないかと考えた。  
失敗の原因が明確でない場合、モデルの判断や回答の生成に時間がかかることもあるのではないかと思った。  
ツールを実装する際は return と raise の使い分けだけでなく、モデルに対してどのような情報を渡すのかについても考慮する必要があると感じた。
